# 02 — 工作流程

## 文档先行（本项目的强制流程）

**任何行为变更，先改文档，再改代码。**

```
① 改 docs/ 对应模块文档
        ↓
② 改代码
        ↓
③ 跑 uv run pytest
        ↓
④ 文档与代码不一致 → 回到 ①
```

**为什么强制**：本项目的历史教训是"界面承诺与代码行为系统性偏离"——7 处已确认偏差，全部是**文档/提示说了但代码没做**：

- "正在用 pro 生成角色系统" → 硬编码 `flash`（`plot_engine.py:239`）
- "写作完成并已保存" → 空响应连盘都没落（`novel_commands.py:341`）
- "剧情笔记写作时会注入 prompt" → 曾未输出 `user_notes`，现已补上回归测试

**文档先行不是为了好看，是因为这个项目已经证明"不先写清楚就会撒谎"。**

### 哪些变更必须走文档先行

| 变更 | 是否文档先行 |
|---|---|
| 新增/修改操作契约 | ✅ 必须 |
| 改失败语义 | ✅ 必须（并更新 `docs/specs/contracts.md`） |
| 新增模块 | ✅ 必须（含模块文档） |
| 改参数语义 | ✅ 必须 |
| 纯 bug 修复（行为恢复到文档已描述的状态） | ❌ 不需要 |
| 重构（外部行为不变） | ❌ 不需要 |
| 测试补充 | ❌ 不需要 |

## 兼容性优先（第一条压倒性原则）

**当一个改动会破坏既有契同时，默认选择是"加别名"，不是"换掉"。**

这不是保守，而是本项目已经踩过的坑：`--tier` 是**贯穿全仓十余处**的参数名（`character_engine` / `plot_engine` / `chapter_writer` / `base_agent` / `deep` / `lightweight` / `cli` / `tui`），配置文件里是 `deepseek_v4_flash` / `deepseek_v4_pro`，测试里固化了 `flash` / `pro`。

**不得破坏的契约清单**（完整版见 [`../docs/specs/deepseek-fastpath.md`](../docs/specs/deepseek-fastpath.md) §2）：

| 契约 | 处理方式 |
|---|---|
| `model_tier: str`（**10 个模块的透传参数**） | **保留为不透明字符串透传**。改签名？不改。加 `ModelRef`？不加 |
| `--tier` CLI 选项 | **保留为弃用别名**，打 stderr 提示，**不删除** |
| `deepseek_v4_flash` / `deepseek_v4_pro` 及 `*_flash` / `*_pro` 后缀 | **全部可解析**（采用 `service.py:347-348` 已有的回退链） |
| `DEEPSEEK_API_KEY` | 一个 Key 覆盖两档 |
| `max_tokens` 4096/8192 与 `ANALYSIS_MAX_TOKENS=8192` 覆盖 | **不得回退**——4096 会截断角色 JSON，那是 A1 事故成因 |
| `budget.max_cny_per_session`（CNY） | 配置**继续写 CNY**，换算在代码里 |
| `tests/test_llm_client.py` 的断言 | **不得为了让新代码通过而修改** |

**判据**：如果一条改动会让用户的既有脚本、配置、或肌肉记忆失效，**先加别名，再考虑弃用**。弃用要有明确的版本边界，不能在同一次改动里既加新又删旧。

### 推论：新能力尽量止步于最外层

新增的**可选**参数（如 `--provider` / `--model`）应当在**最外层入口**就地解析，**不要**把新概念穿进内部 API。

**判据**：一条改动如果让内部调用链多了一个参数，先问"能不能在外层消化掉"。能就不往下传。

反例（我原计划里的错误）：为支持 `--provider/--model` 而给 10 个模块的 `model_tier` 参数换概念。**`tier` 本身就能表达"多级模型"的语义**——便宜档做大纲、强档写正文，这是一个 tier 问题，不是 provider 问题。

## 任务流程

```
1. 读 plan/README.md       → 确认铁律
2. 读 plan/00-phases.md    → 找自己在哪一阶段
3. 读 plan/01-tasks.md     → 取任务、看前置、看写入范围、看验收
4. 前置未满足 → 停，不要硬做
5. 任务涉及行为变更 → 先改 docs/
6. 写代码
7. 跑验收命令
8. 更新 plan/README.md 的阶段状态 + 勾掉 01-tasks.md 该项
9. 提交
```

### 取任务时先回答三个问题

1. **前置满足了吗？** 不满足就停——阶段之间有真实依赖，跳做会返工。
2. **写入范围是什么？** 越界会与并行 agent 冲突。
3. **验收标准里哪条最难？** 先做最难的那条，早失败早发现。

## 并行协作规则

P3 的 CLI / MCP 适配器、P1 的各模型、P4 的各调用点**可以并行**。并行时：

- **文件不重叠**。取任务前先看 `写入范围`，两个任务范围相交时**串行做**。
- **共享文件串行**。`src/tools/result.py`、`pyproject.toml`、`docs/specs/contracts.md` 是热点，改动前确认没有其他人在动。
- **契约先冻结**。P2 的 `NovelResult` 定下来之后 P3/P4 才能并行——**不要边改契约边用契约**。

## 提交规范

```
<type>(<scope>): <中文描述>
```

一次提交做**一件事**。不要在一个提交里同时改契约和改实现。

**提交前必跑**：

```bash
uv run ruff format . && uv run ruff check --fix .
uv run mypy src
uv run pytest            # 必须全绿，且不联网
```

## 遇到失败怎么办

| 情况 | 做法 |
|---|---|
| 测试红了，原因不明 | 先跑 `uv run na-tools-doctor`；再确认是不是环境问题 |
| 验收标准达不到 | **停下来问**，不要降低标准或绕过 |
| 发现计划里没有的缺陷 | 记录到本文件末尾的「待登记」，**不要顺手修** |
| 需要扩大范围 | 先问 |
| 前置任务没做完 | 停，不要替别人做 |
